# TaxTransGeneralJournalAccountEntry

Added after checking the existing TaxTrans, GeneralJournalAccountEntry, subledger entities, model conventions and migration history. This table did not previously exist in code or ERM.

The entity follows the existing Finance `Entity<long>` convention and is mapped in Tax. All 17 supplied columns are represented. The inherited `RowVersion` property maps to the SQL `SysRowVersion` column, generated by SQL Server. Existing shared audit/soft-delete fields are retained; the table therefore also has the project's seven additional audit/state columns.

The five record references use nullable 64-bit integers. In particular, `TaxUncommitted` is a record reference, not a boolean. `TaxTransRelationship` and `MonetaryAmountType` retain integer codes; no unverified enumeration labels were invented. Zero references and an empty transaction currency remain valid, as in the supplied export. Currency length follows the existing three-character project constant.

AccountingCurrencyAmount, TransactionCurrencyAmount and AllocationFactor use `decimal(32,6)` to preserve six-decimal values. The table has non-unique company/reference indexes for GeneralJournalAccountEntry, TaxTrans and SubledgerJournalAccountEntry. Optional D365 zero references are not converted into mandatory SQL foreign keys.

Company filtering and soft-delete filtering come from the existing ApplicationDbContext conventions. The table is classified as transaction storage for seed coverage. Configuration/master preparation and production posting services remain unchanged; association fixtures are created only through the explicit seed flow below.

Migration: `20261118072539_AddTaxTransGeneralJournalAccountEntry`. Its Up operations create only this table and three indexes. Its Down operation drops only this new table.

Reference: [Microsoft Common Data Model table metadata](https://learn.microsoft.com/en-us/common-data-model/schema/core/operationscommon/tables/finance/tax/transaction/taxtransgeneraljournalaccountentry).
## Seed coverage

The opt-in `AddFoundationTransactionExamples()` flow now calls `TaxTransGeneralJournalAccountEntrySeeder` after the service-posted AP-04 journal is reconciled. Association IDs are returned in `FoundationTransactionReport.TaxAccountingAssociationIds`. Configuration/master preparation does not insert transactional associations.

For already-posted fixtures, call `TaxTransGeneralJournalAccountEntrySeeder.SeedAsync(taxRecordIds)` in the required company context. IDs must be resolved from existing tax records; no exported sample IDs are used. This seeder creates associations only: it neither changes existing postings nor creates parent records.

The supported fixture is a unique, nonzero input-tax ledger entry. Matching requires the same company, voucher, accounting date, configured input-tax dimension, tax posting type, transaction currency, accounting amount and transaction amount. The dimension, main account and currency must exist in the same company. Missing, ambiguous, shared/allocation or conflicting associations fail without partial inserts. A serializable transaction protects the check-and-insert operation; reruns preserve existing matching IDs. Existing conflicts are never repaired silently.

`TaxUncommitted`, `SubledgerJournalAccountEntry`, `TaxTransRelationship`, `MonetaryAmountType` and `AllocationFactor` remain null: these fixtures have no verified source for those values. This is scoped association seed coverage, not implementation of all D365 tax relationship types or a change to production posting services.

## Live relationship checks

After applying `20261013110000_BackfillSalesLineOriginLinks`, the local database had 14 active sales lines with inventory transaction IDs and 14 active `InventTransOriginSalesLine` links. Missing or orphaned active links: **0**. Active lines without headers, origins, or inventory transactions: **0**. Duplicate active origin links and orphaned inventory transactions: **0**. Active confirmation lines without journals and journals without lines: **0**. Active line/header charges without their document: **0**. Sales line open demand versus inventory transaction demand, header gross amount versus active line amount, and `InventSum.OnOrder` versus active sales demand all had **0 mismatches** at the checked precision.

The backfill inserted links only where an active line, active order, and active origin matched by company, inventory transaction ID, and sales ID. It did not alter sales quantities or inventory amounts. The migration is repeatable because it skips active links that already exist.

Additional active-reference checks found **0** orders without customers or invoice accounts, lines without items or inventory dimensions, orders or lines with missing delivery addresses, postal addresses without locations, and lines referencing missing tax groups or item tax groups.

The latest local check had **16** non-deleted sales lines with inventory transaction IDs and **0** missing or orphaned origin links. Earlier detailed checks also found no missing origin rows or missing order or line delivery addresses. The labeled replacement test used order `SO-2026-000015`: postal addresses 7 and 9 were soft-deleted after replacement, address 10 was soft-deleted after deleting its line, and current header address 8 remained active. Each address's location had the corresponding state. The test order was canceled after verification.

A second labeled API test used order `SO-2026-000018`: its header percentage charge recalculated from 0 to 1 after adding a 10 SAR line, to 2 after editing the line to 20 SAR, and to 0 after deleting the line. Discount recalculation also completed with the charge remaining consistent. A focused regression confirmed that confirmation records a zero amount when a percentage charge has a zero net basis. The test order was canceled.

A third labeled API test used order `SO-2026-000019`: a USD sales charge against the SAR order was rejected; a charge with no supplied currency was saved in SAR. The order was canceled after verification.

The `PriceDiscTable` model previously defined unconditional foreign keys from `AccountRelation` to `CustTable`, `ItemRelation` to `InventTable`, and the optional `InventDimId` to `InventDim`. Those constraints rejected valid group/all and dimension-independent agreements. Migration `20261013130000_RemoveInvalidPriceDiscForeignKeys` removes those three constraints while retaining lookup indexes. It was applied to the local database; a metadata query found no remaining `PriceDiscTable` foreign keys, and the EF model-snapshot tests pass. The migration's `Down` does not recreate invalid constraints because valid group/all rows could then make rollback fail.

A fourth labeled API test saved a temporary group price agreement for item `ITM-1001` and price group `PGAUDIT`. Order `SO-2026-000020` selected its 7 SAR price for a BTL line. The temporary agreement was deleted and the order canceled afterward. Agreement matching now uses the sales order date and allows the existing generic-currency flag.

The full `IXApi.Tests` assembly passed **239 tests**, with 2 existing skips, using an isolated output directory. The focused Sales Order, inventory, markup, and price relationship filter passed 16 tests. SalesTable and SalesLine polymorphic table numbers are now defined once in `FinanceTableNumbers` and used by order, confirmation, and markup services.

## Coverage limits

- The local database has 4 UOM conversion rows, 0 rows in the additional UOM support tables, and 0 active `MarkupAutoTable`/`MarkupAutoLine` rules. Conversion and one temporary group price agreement were exercised. Automatic-charge application cannot be validated with this data; no automatic-charge application service is wired to Sales Order creation in the current code.
- Most Sales Order relationships are logical application relationships. This audit checked active row consistency and removed three invalid `PriceDiscTable` SQL foreign keys; it did not introduce new SQL foreign keys.
- These checks cover implemented API paths and the listed local data, not every possible tax, currency, return, warehouse, concurrency, or production-data combination.
- UI actions for purchase orders, direct delivery, holds, notes, credit notes, charge allocation, sales-tax drilldown, delivery-date calculation, supplementary items, tiered charges, price push, pro forma confirmation, and service agreements have no implementation in this Sales Order page and are disabled. They need separate backend and page work before they can be validated as functional.
